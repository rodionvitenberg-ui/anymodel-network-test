# Итоговый отчёт: антицензорный шлюз для доступа к AI-сервисам из РФ

*Дата: 2026-11-05, обновлено 2026-11-07. Статус: реализация, локальная валидация и боевой деплой завершены (раздел 8); замеры выполнены дважды — серия 2026-11-05 и полная перепроверка 2026-11-07 на выделенном VPS с портом 443 (раздел 4, `benchmarks/results/summary.md`). Важное уточнение 2026-11-07: точка А замеров физически находится в **Бишкеке (KG)**, а не в РФ — прежняя формулировка «замеры из РФ» была ошибочной; на этом пути ТСПУ нет, поэтому проверка из РФ выполняется проверяющим (раздел 9). Обновление 2026-11-06: клиентский вердикт + повторная E2E-верификация боевого доступа (раздел 9).*

## 1. Ситуация с фильтрацией (кратко)

Детальный разбор — в [`research/dpi-overview.md`](../research/dpi-overview.md). Ключевое:

- **ТСПУ** — DPI-оборудование на сетях всех операторов РФ под централизованным управлением РКН; операторы не контролируют правила ([HRW, 07.2025](https://www.hrw.org/report/2025/07/30/disrupted-throttled-and-blocked/state-censorship-control-and-increasing-isolation)).
- **Мертвы или почти мертвы**: WireGuard и OpenVPN (сигнатурная блокировка с 08.2023, [bbs#274](https://github.com/net4people/bbs/issues/274)), Shadowsocks-legacy и VMess+WS+TLS (детект TLS-in-TLS с 05.2024, [bbs#363](https://github.com/net4people/bbs/issues/363)).
- **2025–2026 — новые методы**: (а) «TCP 16-20» — заморозка соединения после ≈15–20 КБ сервер→клиент в одном TCP-соединении к «подозрительным» ASN на мобильных сетях ([bbs#490](https://github.com/net4people/bbs/issues/490)); (б) whitelisting TLS-fingerprint'ов; (в) частичные блокировки диапазонов Cloudflare (март 2025, HRW); (г) поведенческая заморозка при шторме параллельных TLS-рукопожатий к одному IP:443 ([bbs#546](https://github.com/net4people/bbs/issues/546), подробно — `research/dpi-overview.md`, п. 2.7).
- **Гетерогенность**: поведение различается по операторам, регионам и даже времени суток — универсальных гарантий не существует, возможна только инженерная оценка с проверкой на конкретной сети.

## 2. Выбранный стек и обоснование

**Xray-core 26.6.27 (сервер, закреплённая версия: с ней совместимы все целевые клиенты, включая Hiddify/sing-box) + VLESS + REALITY (flow `xtls-rprx-vision`), TCP 443, docker compose, клиентский fingerprint `chrome`, клиентское ядро xray 26.10.31.**


Почему устойчиво к текущим методам:

| Метод ТСПУ | Ответ REALITY |
|---|---|
| Блок по SNI | SNI = крупный легитимный сайт (`www.samsung.com`); блок = коллатеральные повреждения. Перегретые dest (microsoft/apple/.ru/.ir/.cn) исключены списком из исходников Xray |
| Блок по сертификату | Сертификата у нас нет: неавторизованные соединения (включая активные пробы DPI) прозрачно редиректятся на настоящий сайт-«одолжитель» |
| TLS-fingerprint whitelist | Клиент маскируется под Chrome (uTLS `fp=chrome`) |
| TLS-in-TLS эвристика (bbs#363) | Vision (`xtls-rprx-vision`) не формирует детектируемый паттерн «3 пакета ≥411 B» |
| Сигнатуры протоколов | Снаружи — стандартный TLS 1.3 + HTTP/2 |
| QUIC-фильтры | Не задействуем: только TCP/443 |

Подробное сравнение с альтернативами (AmneziaWG, Hysteria2, Trojan) и остаточные уязвимости — в [`research/protocol-comparison.md`](../research/protocol-comparison.md). Главные остаточные риски: **IP-репутация ASN** и **TCP 16-20 freeze** на мобильных; обе митигации (смена IP, клиентский фрагментатор ByeDPI, запасной CDN-транспорт) описаны в отчёте ниже.


## 3. Реализация

- Деплой — [`deploy/`](../deploy/): `install.sh` (два шага: clone → run), `docker-compose.yml` с host-сетью и пиннед-образом `ghcr.io/xtls/xray-core:${XRAY_VERSION}` (сейчас **26.6.27**; тег = версия релиза без `v` — проверено workflow `.github/workflows/docker.yml`, скрипты нормализуют `v`-префикс), генерация всех секретов на сервере, идемпотентный ре-ран, fail-fast валидация конфига (`xray run -test`) до рестарта.
- Конфигурация: один VLESS-inbound на 443 с REALITY (dest=www.samsung.com, x25519, shortId), sniffing для маршрутизации, routing-правило blackhole на приватные подсети (защита от SSRF в LAN/метаданные облака 169.254.169.254).
- Клиентский профиль: `gen-client-profile.sh` → VLESS-строка + QR (`qrencode`), совместим с v2rayNG/Streisand.
- Клиент ПК (без сторонних приложений): [`client/install.sh`](../client/install.sh) разбирает VLESS-строку (или стягивает секреты с сервера по SSH) и ставит локальный Xray-клиент systemd user-сервисом `anymodel-gw`: автостарт при входе в систему, `Restart=on-failure`, системный прокси браузера включается на старте и снимается `ExecStopPost` при остановке. Секреты — `~/.config/anygateway/client.env` (600, вне git, переживают ребут).

## 5. Ограничения и риски (честно)

1. **Замеров из сети с ТСПУ нет и быть не может у исполнителя.** Обе серии (2026-11-05 и 2026-11-07) сняты из Бишкека (KG) — там ТСПУ отсутствует; доступа к сети РФ у исполнителя нет, поэтому цифры характеризуют шлюз и канал, но не фильтры РФ. Проверка из РФ — на стороне проверяющего: доступ (адрес + VLESS-строка) выдан в `report/private-access.md`, скрипты батареи готовы, один прогон занимает ~3 минуты.
2. **TCP 16-20 freeze** ([bbs#490]): на мобильных сетях стриминг LLM-ответа одним соединением может замерзнуть после ≈15–20 КБ при «плохом» IP. Митигации: IP вне «подозрительных» ASN; клиентский фрагментатор (ByeDPI/GoodbyeDPI); запасной транспорт VLESS+WS+TLS через Cloudflare (требует домена, конфигурация — план Б, не включена в деплой сознательно).
3. **IP-репутация**: Hetzner/DO/OVH и др. периодически блокируются по подсетям. Рекомендовано: проверка IP перед покупкой, запасной IP, смена dest за минуту.
4. **Гетерогенность ТСПУ**: результат на одном операторе не переносится на другой; нужен прогон на сети конкретного пользователя.
5. **Версия сервера закреплена (26.6.27) — ради совместимости со всеми клиентами.** Клиенты проекта живут на двух разных ядрах: собственные установки на xray и сторонние приложения (Hiddify) на sing-box. REALITY-аутентификация в Xray-core ужесточалась (26.7.x — `minClientVer`, 26.9.9+ — обязательный пост-квантовый key share `X25519MLKEM768`), поэтому версия сервера выбрана заранее и закреплена: **26.6.27** — на ней одинаково работают v2rayNG, Streisand, `client/install.sh` и Hiddify (проверено матрицей на реальных бинарниках, `benchmarks/scripts/compat-matrix.sh`). Обратная сторона: серверное ядро не обновляется автоматически — только через прогон этой матрицы. Детали: `docs/adr/0001-server-pinned-26.6.27.md`, `client/README.md`.
6. **Асимметрия аплоада**: через туннель аплоад оказался ниже базовой линии (1.10 vs 3.04 МБ/с в серии 2026-11-07). Пик CPU при этом — 19.7% одного vCPU, то есть причина не в шлюзе, а в сетевой части: высокое произведение полосы на задержку (BDP: ~40 Мбит/с × RTT 160 мс ≈ 800 КБ данных «в полёте») при инкапсуляции TCP-в-TCP через локальный userspace SOCKS5 без агрессивного тюнинга буферов сокетов (`tcp_wmem`/`rmem`) и алгоритма контроля перегрузки TCP BBR. Для LLM-сценария (даунлоад стрима) не критично, но при больших загрузках в сторону сервера заметно; митигации — BBR и увеличенные буферы на обеих сторонах.
7. Не реализовано: UDP-фоллбек (Hysteria2), multi-user (ротация shortId под каждого пользователя), автоматическая смена dest при падении. Осознанно (YAGNI), легко добавляется.
8. **Лимит параллельных TLS-рукопожатий** ([bbs#546](https://github.com/net4people/bbs/issues/546)): по сообщениям сообщества с конца 2025 ТСПУ на части сетей применяет поведенческую заморозку — если одновременно совпадают «подозрительный» ASN хостера, типичный прокси-профиль и залп параллельных TLS-рукопожатий (>3–5 подряд к одному IP:443), трафик замораживается на ~120 с сразу после TLS Finished при живом TCP и отвечающем пинге. Боевой профиль проекта (запросы к LLM — единичные соединения со стримингом) под это не попадает, а нагрузочный скрипт `parallel-load.sh` (50–200 одновременных сессий `generate_204`) — ровно такой профиль: при его прогоне из сети РФ возможна временная (~120 с) заморозка, которая снимается сама. Митигации для продакшена — мультиплексирование (mux/xmux) или транспорт **VLESS + XHTTP (SplitHTTP) + REALITY** с паддингом (`xPaddingBytes`). Собственного замера из РФ у проекта нет (точка А — KG), поэтому механизм зафиксирован по сообщениям сообщества, а не по собственным измерениям.

## 6. Затраченное время

Суммарные трудозатраты — **≈3.5–4 часа чистой инженерной работы в 4 итерации**:

- Итерация 1 (исследование → реализация → валидация → документация): **≈40 минут** (09:45–10:25 UTC).
- Итерация 2 (2026-11-06: проверка клиентов и доступа, публикация репо): **≈25 минут**.
- Итерация 3 (2026-11-06: матрица «версия сервера × клиент» на реальных бинарниках, выбор и закрепление версии сервера 26.6.27, скрипт `compat-matrix.sh`): **≈1 час**.
- Итерация 4 (2026-11-07, перепроверка и замеры на новом стенде: полная батарея `parallel-load.sh` + `server-benchmark.sh`, новые CSV/график, повторная выдача профиля): **≈1.5 часа**.
- Ожидаемые затраты на боевой деплой у пользователя: **10–15 минут** + прогон бенчмарков ~30 минут.

## 7. Выдача клиентского профиля (сервер)

После запуска `install.sh` на вашем VPS: `deploy/scripts/gen-client-profile.sh` печатает VLESS-строку и QR — импорт в Hiddify (sing-box), v2rayNG ≥ 2.3.15 / Streisand или `client/install.sh` на ПК; сервер пиннится на Xray-core 26.6.27, поэтому проходят все четыре клиента (раздел 5, п. 5).


## 8. Фактический деплой (боевой сервер, 2026-11-05)

- **Сервер**: Webdock.io ApS (Копенгаген, Дания, AS44803), Ubuntu 26.04 LTS — вне РФ, ASN вне «первого эшелона» подозрительных (не Hetzner/DO). Реальный адрес/домен в репозиторий не коммитятся (см. `report/private-access.md`, gitignored).
- **Отклонение от базовой архитектуры**: TCP 443 занят живым nginx, обслуживающим 10+ действующих сайтов этого сервера. Перекраивание nginx (stream SNI-passthrough с переносом всех vhost'ов) признано недопустимо инвазивным для общего продакшна → REALITY развёрнут на **порте 8443** (`install.sh <IP> [SNI] [PORT]`). Компромисс: non-443 порт заметнее для DPI (предупреждение самого Xray). План Б при давлении ТСПУ на 8443 — миграция на 443 через nginx stream ssl_preread (отдельная согласуемая операция).
- **Проверено на сервере**:
  - контейнер `xray-reality` запущен (host-сеть, порт 8443);
  - анти-проба: openssl-зонд к :8443 с SNI samsung получает **настоящий сертификат CN=www.samsung.com (DigiCert)** — REALITY-маскировка работает;
  - E2E на сервере: curl→socks→xray-клиент→REALITY→xray-сервер→интернет: Google `HTTP 204` (0.13 c), `api.openai.com` → `HTTP 401` (ожидаемо: ответ API без ключа, т.е. AI-API **достижимы**);
  - порт 8443 доступен извне (зонд из внешней сети получает сертификат samsung), ufw-правило активно.
- **Гигиена**: секреты шлюза (UUID/ключи) хранятся только на сервере в `deploy/.env` (права 600, владелец root) и не покидают хост.

### 8.1. Миграция на выделенный VPS и стандартный порт 443 (2026-11-07)

Общий сервер с nginx на 443 вынуждал non-443. Шлюз перенесён на выделенный VPS и переведён на **443** ([ADR 0002](../docs/adr/0002-reality-on-port-443-dedicated-host.md)):

- **Новый сервер**: `<SERVER_IP>`, Ubuntu 26.04 LTS, 1 vCPU / 1.6 ГБ, Webdock (Копенгаген, DK, AS44803); чужих сервисов нет, ufw не включён — 443 открыт по умолчанию, Docker ставит сам `install.sh`.
- **Порт 443**: туннель неотличим от обычной HTTPS-сессии. Контейнер работает от root (`user: "0:0"`): непривилегированный uid образа (65532) не может занять порт <1024 даже с `cap_add NET_BIND_SERVICE` — проверено, ошибка `bind: permission denied`.
- **Проверено с клиентской машины** (Бишкек, KG; внешний IP клиента в отчёте не публикуется):
  - анти-проба: openssl-зонд к `<SERVER_IP>:443` с SNI `www.samsung.com` получает настоящий сертификат `CN=www.samsung.com` (Samsung SDS Co., Ltd. / DigiCert), а HTTPS-запрос — 301 от Samsung: маскировка живая;
  - **Hiddify (sing-box 1.14.4, его штатное ядро)**: `generate_204 → 204`, `api.openai.com → 401`, exit-IP = `<SERVER_IP>`;
  - xray-клиент 26.10.31 (его ставит `client/install.sh`): `204 / 401`, exit-IP = `<SERVER_IP>`;
  - ПК-клиент переустановлен на новый профиль: `anymodel-gw` active, системный прокси `manual`, `curl -x http://127.0.0.1:10809 … generate_204 → 204`.
- **Прежний сервер**: контейнер `xray-reality` остановлен и удалён, каталог проекта и ufw-правило 8443 сняты; nginx на 443 (10+ действующих сайтов) не затронут. Секреты прежнего шлюза отозваны вместе с сервером — профиль выдан заново.
