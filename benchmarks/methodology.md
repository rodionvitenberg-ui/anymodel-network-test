# Методика нагрузочного тестирования

## Участники замера

- **Точка А (клиент)**: машина конечного пользователя в сети его оператора. Замеры ведутся дважды: (а) напрямую — базовая линия; (б) через туннель (локальный socks клиента, порт 10808).
- **Точка Б (сервер)**: VPS с деплоем из `deploy/`. Там же снимается стоимость ресурсов (`server-benchmark.sh`).
- **Где именно снимались замеры 2026-11-07**: точка А — Бишкек, Кыргызстан (AS42837 Extra Line LLC), внешний IP клиента (в публичных документах скрыт); точка Б — выделенный VPS (Webdock, Копенгаген, DK). **На пути из KG нет ТСПУ** — поэтому эти цифры характеризуют сам шлюз и канал абонента, но НЕ поведение российских фильтров. Проверка из РФ — отдельный шаг проверяющего (доступ выдаётся в `report/private-access.md`).

## Батарея тестов

### 1. Пропускная способность (базовая линия vs туннель)

Один и тот же эндпоинт в обоих режимах — иначе сравнивать нельзя:

```bash
# короткая батарея (ping/TTFB/даунлоад/freeze 50 МБ):
SERVER_HOST=<IP> LOCAL_SOCKS_PORT=10808 ./benchmarks/scripts/run-benchmark.sh <label>

# расширенная батарея (базовая линия, параллельные потоки, latency под нагрузкой,
# аплоад, большое односоединение, конкуренция 50/100 сессий):
SERVER_HOST=<IP> LOCAL_SOCKS_PORT=10808 ./benchmarks/scripts/parallel-load.sh <label>
```

`curl -w '%{speed_download},%{time_total}'` к `speed.cloudflare.com/__down`, напрямую и через `--socks5-hostname 127.0.0.1:10808`. Если direct ≈ tunnel — узкое место канал абонента, а не шлюз. iperf3 не обязателен: клиенты проекта работают через socks (не TUN), а `proxychains` сам добавляет userspace-оверхед.

### 2. Latency под нагрузкой

- Базовая: `ping <IP>` (RTT до VPS) — 10–15 проб.
- Под нагрузкой: `ping` и `curl -w %{time_starttransfer}` параллельно с 4 потоками по 25 МБ. Смотрим рост RTT/потери — признак переполнения буферов на пути.
- Прикладной уровень: TTFB `api.openai.com` напрямую и через туннель — то, что реально чувствует LLM-клиент.

### 3. CPU/RAM сервера

`server-benchmark.sh <секунды> <порт>` (от root на сервере) снимает раз в секунду: `docker stats` контейнера шлюза, `rx_bytes`/`tx_bytes` интерфейса, `loadavg` и число установленных соединений на порту REALITY. Метрики: пик CPU (в процентах одного vCPU), пик RSS, максимум одновременных соединений.

### 4. Параллельные соединения

`parallel-load.sh` гоняет N одновременных потоков (4×10 МБ, 8×5 МБ) и считает агрегат по wall-time, а затем — параллельные мелкие сессии (`generate_204`), по умолчанию 50 и 100; список настраивается: `SESSIONS="50 100 200" ./parallel-load.sh <label>`. Метрики: доля успешных, средний и максимальный TTFB, рост задержки. Это и есть «сколько потоков/сессий выдерживает конфигурация» на этом канале.

### 5. «Тревожность» трафика для фильтров (эмпирика)

Фильтры ТСПУ не отчитываются, но по [bbs#490] известен объёмный триггер ≈15–20 КБ сервер→клиент в одном TCP-соединении к «подозрительным» IP. Тест: непрерывная загрузка через **одно** соединение (curl, без range-запросов) на 50 МБ и на сотни МБ — фиксируем момент «заморозки» (соединение висит без данных).

Отдельный риск — **профиль самого нагрузочного теста**: по сообщениям сообщества с конца 2025 на части сетей РФ ТСПУ замораживает трафик на ~120 с при шторме параллельных TLS-рукопожатий (>3–5 подряд к одному IP:443) от «подозрительного» ASN ([bbs#546](https://github.com/net4people/bbs/issues/546), разбор — `../research/dpi-overview.md`, п. 2.7). Прогон `parallel-load.sh` на 100–200 одновременных сессий `generate_204` из сети РФ как раз даёт такой профиль, поэтому возможна временная (~120 с) блокировка, которая снимается сама; в боевом сценарии (запросы к LLM — единичные соединения со стримингом) профиль не возникает, а при необходимости лечится мультиплексированием (mux/xmux) или транспортом VLESS + XHTTP + REALITY. Результат прогона из РФ фиксируется отдельной пометкой, чтобы не смешивать его с фильтрацией объёмного триггера.

**Честная оговорка:** этот тест даёт ответ только при замере из сети, где ТСПУ присутствует. Замер 2026-11-07 сделан из KG, где ТСПУ нет — он доказывает, что шлюз держит 512 МБ в одном соединении, но ничего не говорит о российских фильтрах. Замер из РФ выполняет проверяющий по той же методике; результат заносится в `results/summary.md` (порог в КБ, оператор, время суток).

## Формат результатов

- `benchmarks/results/YYYY-MM-DD-<оператор>.csv` — сырые замеры (коммитим агрегаты, сырые дампы — в `results/raw/`, игнорируются).
- Сводные таблицы и графики — `benchmarks/results/summary.md` + `charts/` (Python + Matplotlib, скрипт `benchmarks/scripts/plot.py`).

## Что уже проверено локально (до VPS)

- `local-smoke-test.sh`: полный путь curl→socks→xray-клиент→REALITY→xray-сервер→интернет — **HTTP 204, конфигурация функциональна** (см. логи в PR/коммитах). Через Docker-контейнер с пиннед-образом — тоже HTTP 204. Это проверка корректности, не производительности: loopback не даёт данных о ТСПУ и реальных каналах.

## Ограничения методики (честно)

1. Замеры в сети с ТСПУ выполняет человек с устройством на конкретном операторе — из рабочей среды доступна только сеть без ТСПУ (в 2026-11-07 это KG).
2. Фильтрация гетерогенна (HRW): результаты одного оператора нельзя переносить на другой.
3. Даунлоад/аплоад меряются `curl` через socks: userspace-сокс клиента добавляет единицы процентов, но главное — обе стороны сравниваются на одном эндпоинте (direct vs tunnel), поэтому вывод «узкое место = канал абонента» устойчив.
4. «Тревожность» фильтров — эмпирика с суточной вариативностью; одиночный прогон не является статистикой.
5. Батарея длится ~3 минуты в вечерний час: состояние канала абонента (а не шлюза) доминирует в разбросе цифр — отсюда прогон из двух даунлоадов разного размера и параллельные тесты в одной серии.
